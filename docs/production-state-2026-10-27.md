# Production state — 27 October 2026

FeeLens NG is an independent, evidence-led public-fee information platform. It is not a government agency, payment processor, application portal, agent or middleman. The verified production snapshot supplied for this work contains 15 MDAs, 77 services, 70 verified fee items and 28 sources. These are point-in-time figures, not runtime constants; this pass did not independently recount production records.

The frontend is React, React Router, Vite and Tailwind; the public catalogue and protected administration interface use the Node/Express API. PostgreSQL holds application data in `feelens_app`, including services, fees, evidence relationships, channels, administration and session data. The live hosting model is cPanel/Apache with Passenger for Node and PostgreSQL; Apache routes `/api` to the application. The admin CMS uses server-side sessions and supports audited content management. Public API routes include health, database health, stats, search, MDAs, MDA services, service detail and sources.

Fee models include fixed, free, range, percentage, formula, variable and unknown. Unknown is not zero or free. Verification statuses include verified, pending, conflicting, unable to verify and superseded. Evidence links, dates and the nature of conflicts should be reviewed alongside the fee; official channels lead users to government services, not FeeLens payment or application facilities. Source provenance for institution logos is recorded in `research/branding/mda-logo-register.json`.

Sentry monitoring is present in frontend and backend, with sensitive data filtering. Security controls include HTTPS deployment, server-side sessions with secure cookies, CSRF checks, rate limiting, input validation, parameterized queries and sanitized audit logs. Operators should verify settings and monitoring after each release. Existing production metadata may be incomplete; some fees and sources require continued review, and official data can change.

On 27 October, PostgreSQL role authentication failed with `28P01` after the role password and application credential drifted. TCP and the Node process remained available. The operator used cPanel UAPI `Postgresql::set_password` to synchronize the role with the existing application credential. Direct authentication and the health and public endpoints passed afterward. The reported record counts remained intact, with no data loss reported. This task did not change credentials, roles, production data or schema.

Operational recommendations: monitor application and DB health separately; investigate classified failures without logging secrets; maintain verified backups and a tested restore; run the read-only smoke check after releases; keep the application credential and PostgreSQL role synchronized through controlled access; review evidence and official channels regularly. See `deployment.md` for the diagnostic and recovery procedure.
